# Session 5.1 — Landing Page, Leaderboard & Setup Flow

## Goal

Replace the "hardcoded level" flow with a real front-end sequence: landing page with leaderboard + Play button → name entry + difficulty select page → into the game. All persistence via `localStorage`, no backend.

## Depends on

Session 4 (`Board` — will now receive level from this flow instead of a hardcoded value), session 5 (`GameController`).

## Supersedes

The "level-select screen" portion of session 7 (`07-ui-overlay.md`). Session 7 should be scoped down to just the in-game HUD and win/game-over screen — landing and setup live here instead.

## Data model (localStorage)

- Key `mcm.leaderboard`: JSON array of entries `{ name: string, score: number, level: "easy"|"medium"|"hard", date: ISOString }`, capped at a reasonable top-N (e.g. top 20), sorted by `score` descending.
- Key `mcm.lastName`: last-used player name string, to prepopulate the name field for convenience.
- Small `src/storage/leaderboard.js` module wrapping all reads/writes: `getLeaderboard()`, `addScore(entry)`, `getLastName()`, `setLastName(name)`. Keep `JSON.parse`/`stringify` calls guarded (try/catch, fall back to empty array) in case of corrupted/missing storage.

## Screens

### 1. Landing page (first thing shown on load)

- Title/logo area.
- Leaderboard: top scores list, e.g. rank, name, score, level badge, date. Show a friendly empty state ("No scores yet — be the first!") if `mcm.leaderboard` is empty.
- Single **Play** button → advances to the name/difficulty page.

### 2. Name + difficulty page

- Text input for player name, prefilled from `getLastName()` if present, with basic validation (non-empty, trim, reasonable max length e.g. 20 chars — disable Play until valid).
- Difficulty select: three buttons/tiles — Easy (4×4), Medium (6×6), Hard (8×8) — single-select, one highlighted as chosen (default to Easy or none until picked, Play disabled until a level is chosen if defaulting to none).
- **Play** button: on tap, `setLastName(name)`, then build the board for the chosen level (reusing session 4's `Board.buildDeck`/`layout`) and transition into gameplay.

## Implementation notes

- Build as plain HTML/CSS overlay screens (same pattern as planned for session 7), toggled via a simple screen-manager (`show(screenName)` hiding others) rather than a router — this is a single-page game, no need for real routing.
- Keep screen state and the eventual score/session data (session 5.2) in a small shared `GameSession` object (e.g. `{ playerName, level, score, ... }`) passed into `GameController`/UI as needed, so later sessions (5.2, 7) have one place to read from.
- Mobile-friendly: large tap targets, on-screen keyboard shouldn't break layout (test with input focused).

## Files touched

`src/storage/leaderboard.js` (new), `src/ui/screens/Landing.js` (new), `src/ui/screens/Setup.js` (new) or equivalent structure, `index.html` (screen markup), `src/style.css`, `src/main.js` (wiring screen transitions).

## Done when

- Cold load shows the landing page with leaderboard (correctly empty-state on first run, correctly populated after any scores exist).
- Play → name/difficulty page works, validates name, requires a difficulty choice, and Play there correctly starts a board of the chosen size using the entered name.
- Refreshing the page preserves leaderboard entries and last-used name (persisted in `localStorage`, verify via devtools Application tab).
